## 1. What Cetele is

A mobile-first **group dhikr tracker**, shipped as an installable PWA. Dopamine mechanics (tap counter, progress
rings, streaks, live collective counter) layered on **real group accountability**, with "never miss twice"
forgiveness so a broken streak doesn't cause permanent quit. A _cetele_ is a circle that splits and completes a
shared dhikr goal together. Full spec: [`docs/PRD.md`](../docs/PRD.md).

Stack: Next.js App Router + React + TypeScript + Tailwind · Supabase (Postgres/Auth/Realtime) · Vercel · PWA, no app store.

**Last work (2026-07-26, latest) — reminders now tell the truth about what can reach you, and the 14-day grid uses the
desktop (no migration; two branches, ff-merged + deleted; all shipped to prod).**
**(A) Push/reminders gating (`push-gate-pwa-install` → `gate-reminder-rows`).** Owner: _"showing the option to send
notifications on the web version without the PWA being installed is misleading"_, then, after the first fix, _"it still
gives the option to turn on reminders for the tasks in my group and since those reminders are through notifications
it's contradicting."_ Both were right, and the second is the one that mattered. **Detection** now keys on the PLATFORM
RULE, not feature presence: the old `needsIosInstall()` required `!("PushManager" in window)`, which is false on iOS
16.4+ (WebKit exposes PushManager and Notification in ordinary tabs while still refusing to deliver). One
`pushEnvironment()` → `ready` | `ios-needs-install` | `unsupported` | `unconfigured`, and **nothing renders until it is
known** (the old code showed a working control then corrected itself, which on a slow paint is indistinguishable from a
control that works). `subscribeToPush` returns a **reason** instead of `null`, so a refusal that slips past the
pre-flight swaps the view to install coaching rather than surfacing a raw `NotAllowedError`; a plain decline stays
silent (D8). New `components/app/install-guide.tsx` carries the numbered Add-to-Home-Screen steps. **The per-task rows
are gated on REACHABILITY** — live if any device is subscribed (times live on the account and dispatch to whichever
device is subscribed, D42, so laptop→phone is a real flow) **or** if this device can receive (one tap from being that
device); inert, dimmed and captioned otherwise. The device count is a `head: true` COUNT on `push_subscriptions` (RLS
already scopes it; no migration) reconciled from each action's own return (D45), counting up only when this device
wasn't already subscribed (the RPC upserts on endpoint). e2e **22 → 24**; the iOS spec was verified to FAIL against the
old detection, so it pins the regression. _Correction worth keeping:_ on the owner's actual iPhone the OLD check DID
fire (they saw the old install card), so `PushManager` is absent in their Safari tab — the "dead toggle on iPhone"
story was **not** what they were seeing; the live per-task switches were. The new detection is still the more robust
one, but the diagnosis was overstated. **Nothing here has been seen on a real iPhone** — the iOS branch is exercised
by UA override in Chromium, which tests the decision, not Apple's behaviour.
**(B) The 14-day grid on desktop.** Owner: _"on the PC view in progress the 14 day view is constricted to like half of
the screen."_ Measured: the card follows the `--container-page` ladder but the grid was pinned at `repeat(14, 2.75rem)`
— 668 px however much room it had, i.e. **44% of the card at 1920**, worse the bigger the monitor. Now
`minmax(2.75rem, 1fr)` + `w-full min-w-max`: phone/tablet unchanged (44 px floor, 668 px content, scrolls — `min-w-max`
means a day can never be squeezed below the tap target, it overflows instead), 1280 → 57×56 in 852 of 860, 1920 →
96×64 in **1396 of 1404 (99%)**. This forced `aspect-square` off the cell (a widened square is as TALL as it is wide
and bursts its row): height now comes from the row ladder `h-11 → lg:h-14 → 2xl:h-16`, duplicated onto the label column
because that is the only thing keeping the two in step. A `max-w-[88rem]` cap keeps an ultrawide from stretching a day
into a letterbox. The group's member breakdown uses the same component and benefits too.

**Before that (2026-07-25) — haptics, the progress track, and the CI break that had been hiding all three (no
migration; three branches, each ff-merged + deleted).**
**(A) `mohidkhanzada/ci-service-role-key` — CI's e2e job had been RED on every push for days, and it was never the
app.** When e2e sign-in stopped sending email and started minting its own magic link with the service role
(2026-07-24), the workflow's inline `.env.local` heredoc never gained `SUPABASE_SERVICE_ROLE_KEY` — so 11 specs across
5 files died at `helpers.ts:31`, reading like a simultaneous regression in auth, routing, groups and reminders. Local
runs stayed green off a real `.env.local`, which is why it went unnoticed while STATUS claimed 22/22. Fixing it exposed
a **second** missing var behind the first (`NEXT_PUBLIC_AUTH_DEV`, which gates the "Dev sign-in" button that
`auth.spec` + `manage.spec` click to test the real `?next=` redirect) — findable only by pushing again, because the
first error masked every spec that would have shown it. Then the mechanism itself: the env is now the **committed
[`.env.ci`](../.env.ci)** (`cp .env.ci .env.local`, service-role key still read from the running stack, never pasted)
plus **`scripts/check-env.mjs`** wired into `pnpm test:e2e` **and** run before `pnpm build` in CI — it names every
missing var and why it matters, in under a second. Verified by reproducing both original failures. New invariant below.
**(B) `mohidkhanzada/haptics-tap-feedback` — three bugs in the tactile layer.** (1) Both vibration "patterns" led with
a `0`; a pattern alternates **vibrate/pause starting with vibrate**, so `[0,30,20,40]` was a 0 ms buzz then one 20 ms
tick — the multi-buzz flourishes the comments described had **never once played**, on any device. (2) The tick fired
from `onClick`, which on touch resolves at **touchend**, so it landed on release and read as lag; feedback now fires on
`pointerdown` while the count stays on `click` (keyboard activation + the ripple/pop stay on the committed tap, with a
timestamp guard against double-firing). (3) `TapPad` branched to the "celebratory" pattern whenever `done` — but `done`
is the **pre-tap** value, so it never fired on the closing tap and fired on every tap _after_ it: the
celebration-marks-a-transition invariant, in the haptic layer. Extracted **`lib/haptics.ts`** (sibling to `lib/sound.ts`)
with the Android-only reality documented in one place — **WebKit has never implemented `navigator.vibrate`, so all of
this no-ops on iOS in Safari and in the installed PWA alike**. The iOS `<input type="checkbox" switch>` trick was
considered and **rejected**: an undocumented side effect is not something a core loop can rest on.
**(C) `mohidkhanzada/progress-track-contrast` — owner-reported "the incomplete ring is barely visible in light mode",
and it measured far worse than subtle.** The track was `--muted`, a large-**area** fill token, used as an 8–18 px
**stroke**: **1.20:1** on a white card, **1.11:1** on cream, **1.10:1** on dark. Worse, the two HERO rings had each
independently decided the track should "recede" — `StatRing` shipped `softTrack={true}` by default and `TapPad`
hardcoded the same trick, both thinning `--muted` to 60% alpha (~1.1:1) — so **the count screen, the ring you stare at
for a whole session, had the faintest track in the app**. New **`--progress-track`** token per theme, held at **≥3:1 on
both surfaces** (WCAG 2.2 §1.4.11): light `#978d77` (3.29 card / 3.04 cream), dark `#736858` (3.08 / 3.35). It is
**sand, not grey, on purpose** — at that luminance the fill/track gap is only ~1.67:1, so the arc is carried by the
**hue** gap; a grey track at 3:1 turns the ring into one flat dark donut. `softTrack` deleted (never once passed
explicitly), `TapPad`'s override deleted, and `ProgressBar` + the hand-rolled bar in the steadfastness board moved onto
the same token so a ring and a bar can't disagree. The **14-day grid** had the same defect from the same token — an
empty day was `bg-muted`, 1.2:1 — fixed by **outlining** the empty cell, not darkening it: filling it with the track
tone would make a missed day visually **heavier** than a barely-touched one (`bg-primary/20`), inverting the intensity
ramp into something that reads as punishment (D8). All verified on the **real** screens at 390 in both themes (count at
0/100 — the worst case — plus 28/100, Today, Progress, the grid), with the cell outline **measured** in-browser rather
than eyeballed. Gates green on all three; pgTAP **316/316**, e2e **22/22**, and CI green on `main` for the first time in
days. _Two traps worth remembering:_ `bg-progress-track` **silently emitted no CSS** for several dev-server restarts
(token resolved, class in the DOM, no rule, no error — the `glow-*` trap again); a clean `.next` did not fix it,
re-touching the source file did, and the production build was always correct. And a `realtime.spec.ts` failure that
looked like the change **wasn't** — it passed 3/3 on the identical tree, though the Kong ping was 200 so §7's signature
did not match.

## 3. How we work

**Ship in increments, verify, then commit.** End commit messages with
`Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.

**Branching (solo; branches yes, PRs optional — D16):**

1. One **feature branch per Linear issue**, named to match Linear's (`mohidkhanzada/cet-N-slug`). Never commit features straight to `main`.
2. Commit increments; **push** to get a Vercel preview URL.
3. **The four gates must all be green** before merge: `pnpm build` · `pnpm lint` · `pnpm exec tsc --noEmit` · `pnpm format:check`. For anything touching the DB or core loop, also `pnpm test:rls` + `pnpm test:e2e`.
4. **Ask the user before merging to `main`** — `main` auto-deploys to production, so that confirm _is_ the approval step (it replaces a PR).
5. On approval: merge (fast-forward), push, **delete the branch** local + remote.

Open a real PR only ad-hoc when a written review trail is wanted (`gh` is installed).

**Two things need explicit owner approval, separately:** merging to `main` (= deploying), and `supabase db push`
(= migrating prod). Never assume one covers the other.

**Migrations** are the only sanctioned path for schema change — `supabase db push`, files named to match the applied
version (no drift). Every new table needs **explicit grants** (0006 set a default-privileges revoke, so a new table
starts at zero for _every_ role, `service_role` included) and **RLS from day one**, pinned by a pgTAP suite.

**Confirm consequential product decisions** with the user, then log them here in "Decisions that still bind."

**Keep the docs in sync:** edit [`docs/PRD.md`](../docs/PRD.md), then regenerate the Word copy with
`python3 scripts/build_prd_docx.py` (stdlib-only; the script _is_ the formatting — edit content there too).

**Track in Linear** (team `CET`, https://linear.app/mohidkz/team/CET) via the Linear MCP — issue state stays in sync
with the code.

**The user prefers concise, scannable docs** — tables and short bullets, not walls of text.

Each of these is a production bug we already paid for. Treat them as constraints, not preferences.

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **The service worker caches static assets ONLY** — allowlist `/_next/static/`, `/icons/`, static extensions. Everything else always hits the network. **CI** (`.github/workflows/ci.yml`): `verify` (lint + tsc + build + format) and `stack-tests` (fresh-stack migration
replay → pgTAP → **check:env** → build → e2e) on every push. **husky pre-commit is the local gate; CI is the backstop.**
The job's env is `cp .env.ci .env.local` plus the service-role key read from the running stack — see the CI invariant
in §4 before changing it, and add any new env-gated flag to **both** `.env.ci` and `scripts/check-env.mjs`.
